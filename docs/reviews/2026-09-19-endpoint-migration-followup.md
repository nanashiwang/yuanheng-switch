# 线路迁移补充审查

## 第一性原理

1. 域名是请求目的地，不是账号、分组或凭据的身份。旧域名不等于旧凭据失效。
2. Codex 的终端和桌面端可以使用不同模型、分组、密钥，不能借线路迁移互相覆盖。
3. 只有明确的元衡托管记录、精确的旧 HTTPS 域名才允许迁移。第三方和官方配置不改。
4. 操作失败必须恢复原配置；能读取新域名不等于已经完成安装包实测。

## 本轮补充

- 分离“是否拥有可用托管凭据”和“是否已使用新线路”，允许旧 CN 用户从官方模式切回元衡。
- 在主动切回元衡、重新应用元衡模式时更新两个 Codex 托管记录中的目标地址。
- 单独配置桌面端/终端时，同步迁移另一个托管记录的旧地址，但保留其余设置和身份。
- 快照包含两个托管供应商，写入中途失败会恢复数据库记录与 Live/profile 配置。
- WorkBuddy 检查整份模型列表：其他行仍走 CN 时不能报告已迁移；其他行属于第三方时不允许作为元衡整文件回滚。
- 不增加后台启动时无条件迁移，不跨域重试收费请求，不修改实际用户配置、服务端或发布版本。

## 对抗性用例

- 旧 CN 配置分别处于官方模式、元衡模式，主动切换/重应用后均使用新地址。
- 切换前创建的供应商路由器在迁移后读取新记录；真实适配器提取新上游地址及原密钥。
- 两个 Codex 供应商除目标地址外的完整记录保持不变；官方 OAuth 文件字节保持不变。
- 注入目录占用导致的模型目录写入失败，确认恢复旧线路、使用模式与配置文件。
- 重复执行迁移幂等；非元衡 URL、相似域名不迁移；无关 TOML 供应商不变。
- WorkBuddy 混合新旧线路不能冒充全量迁移成功；第三方模型行阻止整文件回滚。

本轮只在本地实施，不提交、不推送、不发布。真实 Windows/macOS 安装后的登录、
会话 Cookie、不同分组流式请求和下载签名仍需正式验收，不能用模拟测试代替。

## 本轮验证结果

- 元衡线路、身份与迁移相关 Rust 测试：61 项通过。
- 历史供应商投影及 `custom` 冲突保护：12 项通过。
- 更新公告、声音克隆：分别 2 项、5 项通过。
- 前端更新配置、模型切换、修复流程及工具卡片：33 项通过。
- 镜像发布离线测试：6 项通过。
- 合计 119 项通过；TypeScript 类型、发布版本一致性、变更格式及差异检查通过。
- 测试使用专用临时目录、内存数据库和假凭据，没有使用用户账号或发起收费模型调用。
